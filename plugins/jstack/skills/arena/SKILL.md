# Arena（多模型并行赛马 + 跨厂商裁判 + 手工嫁接）

启动任何子代理前，先在 todolist 里建好 6 个阶段：`Frame → Fan out → Cross-judge → Pick → Graft → Verify`。

## Phase A：定题与打分表（Frame）

所有候选者拿到完全相同的任务书，任务书就是唯一契约。

1. **明确产出物**：写清每个候选者必须交付什么工件（代码实现、架构方案、验证脚本等）。
2. **写 3–6 条具体可打分的 rubric**：只用于 Phase C/D 评审，**不发给候选者**。每条必须是可观测判据，不是“代码写得好”。
3. **挑选多厂商参赛选手**：
   - 在 Cursor 中用原生 `Task` 并发派出至少 2–3 个不同厂商的强模型（例如 Claude 系 + GPT 系 + Gemini 系；若某个 model slug 被拒绝，改用同家族最近有效 slug 或记一次 dropout，至少保留 2 名选手并如实说明）。
   - 在 Codex 中可并发 `spawn_agent` 跑不同方向，并按 `../jstack/references/host-dispatch.md` 通过 `scripts/run-external.mjs` 引入本机 `claude` 作为跨厂商参赛或裁判视角。
4. **严格隔离输出位置（先拆分再串行化）**：每个候选者分配独立 git worktree（或独立 `/tmp/arena-<slug>/candidate-<n>/` 目录），绝不共享写入目录。

## Phase B：并发开跑（Fan out）

在同一轮中并发派出全部 N 名候选者（`run_in_background: true`），给每一名完全一致的任务书、共享背景路径、各自独立输出目录，并要求附上简短说明：**考虑过哪些备选方案、否决了什么及原因**。

若某名候选者中途失败未产出，继续用剩下 N-1 名并如实记录 `dropout`，绝不隐瞒。

## Phase C：跨厂商只读裁判（Cross-judge）

全部候选者完成后，派出一名**与当前主会话模型不同厂商**的只读裁判（Cursor 用跨厂商 `model` + `readonly: true`；Codex 用 `scripts/run-external.mjs` 调 `claude`）：
- 仅向裁判提供各候选者的**脱敏路径标签**（不暴露模型名）与 Phase A 的 rubric；
- 要求裁判逐条 rubric 打分，并推荐一个最佳底座。
- 若无法完成跨厂商校验（例如外部通道 dropout），如实标注，绝不假装跑了跨厂商裁判。

## Phase D：主会话通读并选底座（Pick）

**主会话必须从头到尾亲自读完每个候选者的完整产物**，按 rubric 逐项打分，绝不凭整体感觉拍脑袋。再把你的评分与 Phase C 裁判对比：
- 双方一致 → 强确认；
- 双方分歧 → 说明有一方带偏见或 rubric 有歧义，仔细重读双方理由再拍板。

选底座的核心标准：**未来维护者最容易扩展且不会破坏不变量的那一版**；两版打平时，选边界更干净、API 更小的那一版（懒惰协议）。

## Phase E：手工嫁接精华（Graft）

再回头通读每一个落败候选者，挑出值得移植进底座的亮点——通常每个落败者只取 **1–2 个真正出彩的点**，绝不机械拼接大段代码。按「第一性原理」把亮点手工揉进底座，保持整份代码在同一套心智模型下浑然一体。

- 如果所有候选者高度收敛到同一形状 → 强共识信号，直接采纳，无需强行嫁接；
- 如果候选者极度发散完全不在一个频道 → 说明 Phase A 题目约束不足，重新定题重跑，绝不硬撮合平均值。

## Phase F：真实验证合成产物（Verify）

像验收任何正式代码一样，在真实运行面与全套测试上验证合成后的最终产物（证明它真的能工作）。若验证暴露出赛马漏掉的缺陷：要么是 Phase A 约束错了（重新定题），要么某个落败者其实防住了它而你漏嫁接了（回到 Phase E），绝不打补丁掩盖。

## 输出要求

交付一份最终合成产物，并附简明合成说明：选了谁当底座及原因、跨厂商裁判的结论（或为何跳过/dropout）、每条嫁接亮点及来源、被否决的方案与理由、收敛或 dropout 情况，以及最终真实验证结果。
