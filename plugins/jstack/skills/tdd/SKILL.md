# TDD（低成本先红后绿回归测试）

当一个 Bug 存在清晰、廉价的本地测试路径时，在改第一行生产代码之前，先把坏掉的行为变成一个**先红后绿**的精准回归测试。

**宁可不加新测试，也绝不写烂测试。** 如果强行写测试需要搭庞大脚手架、写满屏脆弱 mock、依赖慢速重型基础设施、或改完就会被删掉，直接跳过新建测试，改用最接近真实路径的可执行回归检验（定向脚本、CLI 复现、真机/桌面驱动或日志断言）。

## 步骤

1. **吃透缺陷**：明确预期行为、当前错误行为、受影响路径与最小可观测复现。
2. **选最窄的可执行检验**：优先复用该路径旁现有的单测、组件测试或集成测试；不要为了满足流程从零造整套测试框架。
3. **先写失败测试（红灯）**：只测用户/调用者能观察到的预期行为，不绑死当前内部实现细节。
4. **改代码前先跑它，确认挂在对的原因上**：如果没改代码它就过了、或者挂在无关的编译/环境错误上，先修正测试再动生产代码。
5. **做最小生产修复**：满足预期行为且不破坏邻近契约。
6. **重跑回归测试（绿灯）**，并跑邻近相关测试确认无波及。

## 护栏

- 绝不为了迎合错误实现去改测试断言；
- 除非预期业务契约确实改变且理由充分，否则不削弱已有断言；
- 保持回归测试聚焦当前 Bug，不顺手大改无关测试夹具；
- 若为偶发（flaky）问题，尽量先构造确定性触发条件并写明锁定的信号。

## 最终汇报

汇报真实证据而不只说“已加测试”：测试名称 + 修复前失败输出 + 修复后通过输出（或说明为何不适合写单测及改用的可执行回归方式）。
