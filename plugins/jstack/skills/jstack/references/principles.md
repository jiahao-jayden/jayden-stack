# 工程原则手册（完整 23 条）

改编自 `pstack` 的 23 条核心原则，按类别收拢于此，保留每条原则的**触发时机、实操标准与反例**，不再拆成 23 个碎片 skill。

---

## 一、核心原则（Core）

### 1. 懒惰协议（Laziness Protocol）
- **何时用**：重构、控制 diff 规模、或手痒想抽抽象层/配置层/传参透传时。
- **怎么做**：把重复的判断收拢到唯一真相源，往下只传最简单的结果标志；用满足当前需求的最小改动解决问题，少写几行直白代码胜过“看起来优雅”的样板代码。

### 2. 底层思考（Foundational Thinking）
- **何时用**：写业务逻辑之前。
- **怎么做**：先定核心数据结构与类型，再定「脚手架与验证工具先于功能」的顺序，想清楚并发执行者之间会共享哪些状态。

### 3. 第一性原理重设计（Redesign from First Principles）
- **何时用**：要把一个新需求硬塞进现有设计，且发现到处要打补丁时。
- **怎么做**：反问“如果第一天就知道这个需求，模块和接口本来该长什么样？”然后直接重构成那个形状，而不是往旧设计上糊一层层特判。

### 4. 质疑前提（Attack the Premise）
- **何时用**：基于同一个假设的修补**连续 2 次**没过同一个检查。
- **怎么做**：立刻停手，把这几次修复共同依赖的那句前提写下来；找一个“如果前提为假结果就会不同”的直接观测实验去测它。看清失败的分布规律而不只是看大小。**前提没写清并测过之前，绝不写下一轮修补。**

### 5. 先减后加（Subtract Before You Add）
- **何时用**：新增能力、重构或重写前。
- **怎么做**：先删死代码、废弃开关、单次调用包装和陈旧兼容路径，把底座削薄后再往上加新东西。

### 6. 降低读者认知负担（Minimize Reader Load）
- **何时用**：审查或整理难追踪的代码时。
- **怎么做**：数一数跳转层数和隐蔽可变状态；合并只被调一次的包装函数，缩小可变变量作用域，让读者不用在五个文件间来回跳就能看懂逻辑。

### 7. 结果导向执行（Outcome-Oriented Execution）
- **何时用**：跨阶段重写或大迁移。
- **怎么做**：直奔目标架构收敛，不为只活几个小时的过渡态设计复杂的兼容层。

### 8. 体验优先（Experience First）
- **何时用**：产品交互、动效、信息密度与实现省事发生冲突时。
- **怎么做**：选用户用着顺手、看着自然的那一侧，不为了实现偷懒牺牲正反动画、遮挡避让或边界体验。

### 9. 穷尽设计空间（Exhaust the Design Space）
- **何时用**：没有现成先例的新交互或关键架构分叉。
- **怎么做**：别在第一个想到的方案上死磕，低成本做出 2–3 个真正有差异的备选原型放在同一个切换器里横评，再选定方向。

### 10. 造杠杆工具（Build the Lever）
- **何时用**：任何重复性迁移、大范围审计、复杂验证或性能基准。
- **怎么做**：写一个可重复执行的脚本、codemod、检查器或验证 harness，而不是纯手工一遍遍肉眼做；工具本身就是评审者可以重跑复核的证据。

## 二、架构原则（Architecture）

### 11. 领域建模（Model the Domain）
- **何时用**：写带状态的逻辑、发现一堆分散的 `if/else` 布尔标志、或跨文件重复假设同一数据形状时。
- **怎么做**：用显式状态机、强类型模型、查表/注册表、reducer 或清晰边界去编码业务规则，消灭散落的条件判断。

### 12. 边界纪律（Boundary Discipline）
- **何时用**：接外部输入、错误处理或写框架适配层时。
- **怎么做**：在系统入口边界一次性校验和解析未知数据；一旦进入内部核心逻辑，信任类型契约，不再处处重复 `typeof x === "object"` 和防御性判空。

### 13. 类型系统纪律（Type System Discipline）
- **何时用**：在 TypeScript / Rust 等强类型语言里设计类型和函数签名时。
- **怎么做**：用联合类型、品牌原语（branded primitives）和不可变结构让非法状态根本写不出来；禁止用宽泛的 `any` / `string` 糊弄内部不变量。

### 14. 操作幂等（Make Operations Idempotent）
- **何时用**：写命令、安装/初始化脚本、同步循环或可能中途崩溃重试的生命周期逻辑时。
- **怎么做**：重复执行两次、或在任意步骤中断后重跑，都能收敛到同一个正确终态，不产生重复数据或半残状态。

### 15. 迁完调用方立即删旧接口（Migrate Callers Then Delete Legacy APIs）
- **何时用**：引入新的内部 API 替换旧接口时。
- **怎么做**：在同一波改动里把所有调用方迁完并彻底删除旧 API；不留“deprecated 过渡期”、不留新旧双轨并行代码。

### 16. 先拆分再串行化共享状态（Separate Before Serializing Shared State）
- **何时用**：多个并发代理、进程或任务可能写同一个文件、分支、key 或状态对象时。
- **怎么做**：先问它们到底需不需要共用一个写入目标——默认给每个执行者独立的文件、目录、worktree 或分支，只在读取时聚合。两个 worker 往同一个 `state.json` 里写不同字段依然是共享可变冲突。只有当单一写入目标属于真实业务不变量时，才用结构化手段串行化（锁文件、单写者、阶段门禁、CAS）；靠 prompt 口头叮嘱不是并发控制。

## 三、验证原则（Verification）

### 17. 证明它真的能工作（Prove It Works）
- **何时用**：每次改完代码、宣称完成之前。
- **怎么做**：直接检查真实产物——沿真实用户路径运行功能、读回真实落盘值/状态、检查真实 diff。代理指标（文件修改时间、子代理自称通过、缓存输出、“编译通过了”）统统不算。检查意外太容易通过或莫名失败时，先怀疑观测方式本身有没有测偏。

### 18. 只修根因（Fix Root Causes）
- **何时用**：修任何 Bug 时。
- **怎么做**：沿着因果链一路追回系统**第一次出错的位置**并在那里修。只有当某个边界状态本身在业务上是合法的，防护判断才算修复；否则只是掩盖坏数据的补丁。

### 19. 拆成可验证切片（Sequence Work into Verifiable Units）
- **何时用**：多步骤迁移、批量修改、拆 commit 和叠 PR 时。
- **怎么做**：把工作切分成小的、每步都能独立跑通验证的单元；前一片没跑绿，不开下一片。修 Bug 时尽量先落红灯复现测试，再在其上落修复。

### 20. 测行为，不测内部实现（Test Behavior, Not Implementation）
- **何时用**：写新测试、改测试或决定要不要保留旧测试时。
- **怎么做**：只断言调用者/用户能观察到的结果与副作用，这样行为坏了测试必挂、只重构内部实现时测试不碎。协议、解析器、状态机优先补属性测试（Property Test）或等价性对比测试。

### 21. 解释清楚每一个数字（Explain the Number）
- **何时用**：采集、相信或汇报任何性能数字（提速、回退、吞吐、延迟、评测分）前。
- **怎么做**：找出真正的瓶颈限制器（limiter），并排除你测到的其实不是目标工作（比如测到了缓存、空操作、报错快退或压测机先饱和）。配合 `benchmark-checklist` skill 的七问核对。

## 四、委托与元原则（Delegation & Meta）

### 22. 保护上下文窗口（Guard the Context Window）
- **何时用**：上下文开始膨胀——大日志、超长文件、反复全局搜索、大规模并发调研时。
- **怎么做**：把繁重读取和原始数据解析交给子代理，主线程只留提炼后的结论、文件路径与关键指针。

### 23. 别在可逆工作上卡着等人（Never Block on the Human）
- **何时用**：想开口问“要不要我顺手做 X”而 X 本身可逆时。
- **怎么做**：直接做完，把结果、取舍和路径交给用户，让用户基于成品纠偏，而不是把人拖进琐碎确认。

### 24. 把教训固化进结构（Encode Lessons in Structure）
- **何时用**：发现自己第二次在口头或文档里重复同一条注意事项时。
- **怎么做**：优先用架构约束 > 类型系统 > 带修复提示的 Lint > 自动化测试把它堵死，文档规则永远排在最后（配合 `correct` skill 执行）。
