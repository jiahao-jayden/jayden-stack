# 核心工程原则（精炼十条）

从 `pstack` 与日常实践提炼出的十条高频准则，遇到取舍时按此拍板。

1. **先质疑前提，再写方案**：如果需求本身基于错误假设或旧限制，先指出再动手，不要闷头把错方向做完。
2. **只修根因，不打症状补丁**：找不到明确因果链就不改代码；如果一个地方反复需要 workaround，停下来重做边界。
3. **不留向后兼容，先减后加**：过时的旧接口、兼容层、migration、兜底 fallback 直接删；改 API 就在同一波把所有调用方迁完并删掉旧接口。动手新增前，先看能不能删掉重复和死代码。
4. **选满足当前需求的最简单实现**：不做预防性抽象，不加用不到的配置层；优先用仓库已有依赖和成熟方案，别从零重造轮子。
5. **模型对齐领域，让非法状态写不出来**：优先用类型系统和清晰的状态机表达边界，把校验留在系统入口边界处，内部流转不再反复防御性判空。
6. **最小可验证切片**：大改动拆成小步、每步都能独立验证的切片；前一步没跑绿，不开下一步。
7. **证明它真的能工作**：编译通过和 lint 通过不等于可用。必须沿真实用户路径运行并观察副作用（UI 状态、落盘文件、数据库行、真实网络包）。
8. **测试测行为，不测内部实现**：重构内部实现时好测试不该碎；关键解析器、状态机、协议层优先补属性测试（Property Test）或等价性对比测试。
9. **把反复踩过的坑固化进结构**：同一类提醒出现两次，优先用架构约束 > 类型 > 带修复指引的 Lint > 自动化测试解决，写进文档放最后。
10. **降低读者认知负担**：代码、提交信息、PR 说明都替下一个人着想——单次使用的逻辑不强行抽 helper，删掉复述代码的无意义注释，用直白精准的命名。
