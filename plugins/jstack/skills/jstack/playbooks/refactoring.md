# Refactoring（整理旧代码）

**你对外部行为契约负全责。结构变，行为一丝不变。** 与 Feature（增行为）和 Bug fix（改错行为）严格区分。

如果清理途中暴露出缺失功能或真实 Bug，把它拆出去另起任务——先把纯结构整理稳稳落在锚定好的契约上。允许重设计，但要明确命名并改走 **Feature**。超大跨模块重构改走 **figure-it-out** skill；本剧本面向聚焦到中等规模的整理。

1. **先锚定现有行为契约**：
   - 追踪受影响子系统摸清当前对外契约，在动任何结构之前先补上行为级特征测试、快照或等价性校验脚本。
   - 如果该区域原本没有覆盖，**先写锚定测试再动结构**。类型检查和 lint 绝不是行为锚定。
2. **指明代码缺少的领域结构**：
   - 按「领域建模」说清这次到底要消灭哪些散落分支或非法状态。原本就清晰直白的“平淡代码”留着别动——重构必须减少分支或消灭非法状态，绝不能多加一层无意义间接跳转。
3. **先定目标形状**：
   - 按「底层思考」和「第一性原理」写清如果今天从零写，模块布局、类型与调用图该长什么样。跨函数/模块边界时，动工前先跑 **architect**。
4. **先减后加**：
   - 先删死代码、折叠单次调用包装、去掉冗余防御校验、清理孤儿引用，再引入新形状。遵循「懒惰协议」——只做抵达目标形状所需的最小改动，“顺手清理也许更好”的投机改动一律回退。
5. **小步保绿迁移，一刀删净旧接口**：
   - 每迈一小步都跑绿行为锚定测试。
   - 重塑 API 时，在同一波改动里迁完所有调用方并立即删除旧 API，绝不留兼容层或新旧双轨路径。
   - 每次重命名后全局抽查真实文件——重命名极易漏掉字符串、配置、注释与文档里的反引用。机械大批量修改可派范围精确的 `worker`（首行读 `worker.md`）。
6. **在真实产物上证明行为等价**：
   - 不能只看“编过了”。较大重塑必须跑等价性验证：新旧输出对比脚本、基线回放对比、或在真实客户端/设备跑通冒烟流程。
7. **校验阅读负担是否真的下降**：
   - 成功标尺只有一个：读者认知负担实打实变低了。如果整个 diff 没有让代码更易读，直接回退。
8. **按清晰顺序整理提交并走 [`opening-a-pr.md`](opening-a-pr.md)**：
   - 先减法提交，再结构迁移提交，再收尾清理提交，每一步保持绿灯。

**回复要求**：改变了哪块结构、用什么锚定的行为、等价性证明结果、阅读负担变化、交付了什么以及回退了什么（确认未引入新行为）。
