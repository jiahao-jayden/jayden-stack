# Playbook：重构（Refactoring）

**结构变，外部行为契约一丝不变。如果发现顺带要加功能或修真 Bug，拆开做，先把纯重构稳稳合进去。**

1. **先锚定现有行为**：动任何结构之前，先追踪当前对外契约并确保有行为级测试、快照或等价性校验兜底。如果目标区域没测试覆盖，先补行为锚定测试——类型检查和 lint 不能代替行为锚定。
2. **确认这次重构真有必要**：写清当前结构到底缺了什么抽象、或多了什么冗余分支。已经清晰直观的“平淡代码”不要为了好看去过度封装；如果改完反而增加了跳转层数和阅读负担，立刻放弃。
3. **跨边界先定目标形状**：确定模块划分、类型边界和状态归属，让非法状态写不出来。
4. **先减后加，一刀迁完**：先删死代码、单次调用包装层、多余防御校验和废弃分支；改 API 就在同一波迁完所有调用方并删掉旧接口，绝不保留新旧并行的兼容层。重命名后全局抽查字符串、配置、注释与文档引用。
5. **小步保绿推进**：每迈一小步都跑一次行为锚定测试，确保每步都绿；机械的大面积迁移可派边界清晰的 `worker`。
6. **证明外部行为等价**：跑完整测试与真实运行路径（大重构加跑新旧输出对比脚本或真机/桌面端冒烟），证明不是“只编过了”。
7. **确认阅读负担真的下降了**：回头看整个 diff——如果没有实打实变简洁，把无价值的“顺手清理”直接回退。
8. **按清晰顺序整理提交并收口**：先减法提交、再结构迁移、再收尾清理，交由 [`ship.md`](ship.md) 收到约定终态。

**回复必含**：动了哪块结构、用什么锚定行为、等价性验证结果、删掉了多少旧代码/复杂度、是否有回退项。
