# Autonomous run（持续运行一个长任务）

**你对退出条件负全责。先定死可机械判定的完成条件，再一轮轮持续推进直到达标，不半途而废。**

1. **首轮开始前定死可证伪的退出条件**：
   - 必须是客观可检查的谓词（如：全部测试绿、复现脚本通过、全部 N 个 PR 已合入主干、图像 diff 归零、性能指标达标）。绝不用“看起来差不多了”。
2. **配置合适的推进/唤醒节拍**：
   - 如果在等外部事件（CI、合并、远端分支更新），配轻量事件监听或轮询；如果无外部事件，按单次验证耗时设定合理轮询间隔（在 Cursor 中可配合内置 `/loop` 命令）。
3. **每轮只做一个最小、可验证的推进**：
   - 仅实施当前证据支撑的最小改动，跑退出条件检验：推进了就 commit，没帮上忙就彻底回退。绝不把“也许有帮助”的试探性代码留着叠加。
   - 按「拆成可验证切片」逐片验收，绝不攒到最后一起测。
   - **三轮熔断**：同一问题连续 3 轮毫无进展或反复踩同一报错时，立刻触发「质疑前提」彻底换思路；若仍属真实死胡同，立即停下上报，绝不空转烧时间。
4. **途中顺带发现的支撑性障碍自己清掉**：
   - 遇到坏掉的脚本、关联小 Bug、抖动验证器、工具报错等，只要可逆且服务于主目标，直接自己修（非本任务主线的大修可单独拆 PR），不要把可逆琐事丢回给用户或弹窗打断。
   - 只在遇到**不可逆操作**（部署、删数据、共享分支 force-push）、**实验无法拍板的纯产品偏好**或**真实死胡同**时停下请人介入。修完旁路问题立刻回到主退出条件。
5. **每轮记一行审计轨迹**：
   - 按 [show-me-your-work](../../ship/references/show-me-your-work.md) 在 TSV 日志里追加一行：改了什么、为什么、证据指针、退出条件是否前移。
6. **达标才停，绝不偷偷降低门槛**：
   - 碰到平台期不直接认输，先换方向突破；真正无解就坦白汇报死胡同，**绝不靠改松退出条件来宣布胜利**。

**回复要求**：退出条件、总迭代轮数、实际落地了什么、回退丢弃了什么、退出条件的最终实测状态与决策日志路径。
