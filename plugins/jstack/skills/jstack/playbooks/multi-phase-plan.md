# Multi-phase plan（产出正式多阶段计划）

**你拥有这份计划的质量，但本阶段绝不写业务代码。计划是一份执行者可以逐框打勾、操作者可以按证据审计的施工单。**

1. **先判别需不需要计划**：如果改动只涉及一两个文件且做法显而易见，直接跳过本剧本——直说“改动很小不需要写计划”并停下（或转 `feature`/`bug-fix`）。
2. **用原型提前拍板开放问题**：
   - 凡是能通过最小实验/原型解决的架构、交互或时序疑问，先按 [`prototype.md`](prototype.md) 跑出实测结论再写计划。
   - 只把“任何实验都定不了的纯产品或个人偏好分叉”留下来问用户。
3. **落盘正式计划文件**：
   - 开头写清：整体改动目标、全部 PR/阶段的落地顺序、以及依赖关系图（标明哪些 PR 彼此独立直接从主干切出、哪些必须等前置合入、每个 PR 允许触碰的文件范围）。
   - 接着**每个 PR / 阶段独立一节**（按「拆成可验证切片」，每个 PR 只承载一个自洽变化及独立证据），包含可勾选的复选框：
     - 前置依赖；
     - 涉及文件与多入口清单；
     - 要实现的那一个核心改动；
     - 用户可见结果；
     - 完整验证项。
4. **测试本身不够，三类验收框必须齐备**：
   一个阶段只有在**单元测试框、真实运行面实测框、性能框（若涉及）**全部勾完才算通过：
   - **真实运行面实测框**：写出真实用户场景、指定设备/运行方式（热更新/真机/桌面端）、正反状态检查与明确通过判据；
   - **性能框（若适用）**：写明指标、探针命令、先测出的主干基准，以及触发失败的红线阈值；
   - 凡是涉及界面交互变动的 PR，显式标为“合入前待用户视觉/交互确认”。
5. **交回计划文件路径并停下**：明确等到用户说“开干”再开始写代码。

**回复要求**：计划文件路径、PR/阶段清单与依赖顺序、标出的待人工把关项，以及目前仍未证实的假设。
