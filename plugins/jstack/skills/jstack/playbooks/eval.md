# Eval（盲评工作流表现）

**你对实验设计与防泄漏负全责。定标尺、严格盲测、亲自复读、综合裁决。**

## 盲测红线（绝对不可违反）

- 候选者可见的任何目录名、文件名或提示词中，**严禁出现** `eval`、`test`、`judge`、`experiment`、`rubric`、`score`、`compare`、`benchmark`、`candidate`、`arena` 等测试元词。
- 给候选者的提示词必须像一条真实用户的自然需求：只说业务目标，不透露评测目的。
- 禁止诱导链路汇报：不要问候选者“你用了哪些 skill 或原则”。只做常规工程要求，**通过真实代码形态与会话 transcript 核查链路执行**，绝不信自述。
- 目录和项目名必须脱敏，起成真实用户会起的业务项目名。
- 不要告诉候选者还有其他候选者存在。
- 裁判可以知道自己在打分，但只能看到脱敏标签（如 `A` / `B`），绝不能看到模型名或变体名。
- 对比两个变体时，由同一个裁判在同一轮、同一标尺下盲评两组产物。

## 执行步骤

1. **定界与打分表（Frame）**：写清正在测试哪个工作流/提示词变体、什么行为算成功；写出 3–6 条具体可打分的 rubric **仅给裁判看**，对候选者完全保密。
2. **搭建脱敏隔离环境**：为每个候选者建独立干净工作目录，布置好真实任务应有的上下文（项目骨架、待测变体对应的 skill）。
3. **写一条自然的用户需求提示词**：真实用户会怎么说就怎么写，零泄漏。
4. **并发派出 N 个候选者**：按 **arena** skill 的 Phase B 并发在各自脱敏目录跑不同模型，发完全一致的提示词。只负责分发、轮询或汇总的杂务代理用轻量模型。
5. **派跨厂商盲评裁判**：按 **arena** skill 的 Phase C 派出与主会话不同厂商的只读裁判，仅提供脱敏标签、产物路径与 rubric。
6. **从真实 transcript 核查链路，不信自述**：检查当前工作区下 `agent-transcripts/` 中对应候选者的记录（绝不跨项目扫描无关私聊目录），核对它实际打开了哪些文件、跑了哪些命令，结合代码形态评判链路遵循度。
7. **主会话通读全部产物并综合裁决**：不要只转发裁判分数；若你的判断与裁判冲突，说明存在模型偏置或 rubric 歧义，深入对比后再下结论。

**回复要求**：待测变体、rubric、各候选者观察笔记、盲评裁判结论、你的综合分析，以及是否推广该变体的明确建议。
