# Hillclimb（反复优化同一个指标）

**你对指标真实性与实验纪律负全责。监督架构、审 diff、守住回退门禁；具体尝试委派给子代理。**

适用于围绕**单一可量化指标**向明确目标持续迭代爬坡。一次性修性能走 `perf-issue.md`，修单个缺陷走 `bug-fix.md`。

**铁律：一次一个假设、一次一轮实测、达标才留、不达标立刻全量回退。** 绝不堆叠未验证的改动，绝不靠读代码宣称“应该变快了”。

1. **先摸清工作负载与架构，再定死指标和停止条件**：
   - 梳理目标代码路径，列出会左右指标的真实负载维度（数据量、历史深度、状态规模、并发度），选出真正复现用户痛点的用例；复现不了先修用例，不要盲爬。
   - 锁定**唯一核心指标**、变好方向、以及“达标目标 + 最低尝试轮次”组成的停止条件（防止第一轮撞大运就草草结束，例如“比基准快 ≥50% 且至少跑 10 轮”）。用户给了数字就直接用，否则先达成一致。
2. **搭建测量脚手架、验证灵敏度，然后冻结它**：
   - 按「造杠杆工具」写出可一键重复运行的基准脚本，并用对比负载验证它确实能区分坏场景和好场景。
   - 冻结前用 [benchmark-checklist](../../implement/references/benchmark-checklist.md) 校验：脚手架必须输出错误计数和实际完成工作量，且采用足够样本（如 N 次中位数，不做单次测量）。
   - 动第一行业务代码前，先记录基准数字，并跑绿回归门禁（必须始终通过的正确性测试）。
3. **打开决策日志**：
   - 按 [show-me-your-work](../../ship/references/show-me-your-work.md) 建立 `decision.tsv`（不提交进 git，保持在工作树外或 gitignore），每轮一行记录：`id / 假设 / 改动 / 前值 / 后值 / 差值 / 回归测试 / 结论(kept/reverted) / 备注`。每开新一轮前先读一遍避免重踩死路。
4. **每条假设必须锚定具体机理**：
   - 写清因果机制（如“把 X 挪出启动热路径，因为它阻塞首屏绘制”），禁止“试试加个缓存”这类空泛猜测。性能指标可借用 `perf-issue.md` 的七条口诀排序假设。
5. **循环实验（每轮只测一个假设）**：
   - 派范围精准的鲜活 `worker` 实施该假设；若同时有多个独立假设，按「先拆分再串行化」各开独立 git worktree 并发试跑。
   - 用冻结脚手架测前后对比，并跑回归门禁。
   - **只接受“提升超过噪声且回归全绿”的改动**；否则全量回退。“可能有点用”的一律不留。
   - 每次保留的改动单独打一个干净 commit（`git add <明确文件>`，绝不 `git add -A`），无论保留还是回退都写入 `decision.tsv`。
   - 无人值守长跑时，可借用 `autonomous-run.md` 的定时唤醒机制（但沿用本剧本的停止条件）。
6. **突破第一个平台期**：
   - 连续几轮被拒卡在平台期时，不要轻易认输：换优化大类、组合差一点成功的思路、重读源码或尝试更大胆的结构改动。但**正确性与代码简洁永远高于数字**——破坏行为的提速必须回退，而保持数字不变却删掉复杂度的简化值得保留。
7. **收尾**：达到停止条件，或剩余思路收益已微乎其微不值得复杂度时停止；绝不降低停止门槛凑“达标”。确实卡死就如实上报，不空转。
8. **按落盘顺序整理提交并走 [`opening-a-pr.md`](opening-a-pr.md)**。

**回复要求**：指标与目标、从基准到最终的变化百分比、总轮次（保留 vs 回退）、每条保留改动一行摘要、`decision.tsv` 路径，以及如果继续深挖你下一步最想试的点。
