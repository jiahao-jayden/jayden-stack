# Trace forensics（分析已有采样）

**你对离线采样产物的诊断负责。**

与 `runtime-forensics.md`（去活进程抓现场）不同，这里采样文件已经躺在磁盘上——它是固定数据集，直接分析它，不要重新跑一遍覆盖它。工具保持通用：`.cpuprofile` / `.json.gz` 用 DevTools 或脚本解析，spindump 用文本工具，`.heapsnapshot` 用堆分析脚本。

1. **识别格式并用对工具**：大体积采样交给只读 `scout` 解析，主会话只保留提炼结论（保护上下文窗口）。
2. **先转成可查询结构再读**：把原始 trace 或堆快照导进 SQLite（每个 sample / frame / node 一行）或结构化汇总表，用查询说话，不要靠 grep 或肉眼硬翻几百万行 JSON。
3. **顺着查询锁定元凶**：
   - CPU/卡顿：查占用时间最长的栈帧并沿调用树追回热路径；
   - 内存泄漏：顺着 retainer chain 从泄漏对象追到 GC Root；
   - Spindump / 卡死：找长期 on-CPU 或阻塞的线程及其等待原因（锁、I/O、IPC）。
4. **准确归因到源码**：
   - 借助采样自带的符号或 sourcemap 把热帧映射到 `文件:行号` 和符号名。
   - **没有完成符号还原的帧还不算诊断结论**——要么把符号解出来，要么坦白写清该采样文件不含符号表。
5. **区分“已证实”与“最强假设”**：
   - 如果手头有成对的前后采样，diff 对比确认变化；
   - 若只有单份采样，明确标出这是“当前采样支持的最强假设”，不是已经对照证实的唯一根因。
6. 吞吐检查点只留一行：`吞吐检查点：n/a，只读离线采样分析`。查明原因后转交 **Bug fix** 或 **Perf issue**，未获要求不直接改代码。

**回复要求**：采样文件与格式、浓缩后的根因发现、源码定位、分析产物路径，以及是否有成对采样对照确认。
