# Playbook：修 Bug（Bug Fix）

**你对根因与回归证明负责。没先复现就不改代码，没跑通真实场景就不算修好。**

1. **先抓现场证据并稳定复现**：收集真实日志、报错输出、请求响应或最小复现步骤；能写成自动化失败测试的，先写一个会挂的测试（红灯）。绝不靠猜直接打补丁。
2. **圈出全部受影响的端与入口**：检查这个问题是否同时存在于用户点名的多个端（桌面端/移动端/CLI/服务端）或相似入口，列进 todo 清单。
3. **深挖根因，不糊症状**：沿着完整调用链和状态流转查清为什么会坏（复杂排查可并发派 `scout`）。对照 `references/principles.md`：如果根因来自坏边界或旧兼容逻辑，直接清掉旧路径而不是再加一层 `if` 兜底。
4. **制定最小修复方案**：跨越模块边界时先定清类型与接口形状，再动手或派 `worker` 实施。删多余代码优先于加新代码。
5. **三轮熔断纪律**：
   - 同一假设改完仍失败超过 **2 次**，立刻停下来重新核实前提与现场数据，不要微调参数碰运气。
   - 同一问题累计修过 **3 轮**仍不通过，**立刻停下**，向用户汇报已试过的方案、真实报错与最小复现，一起重新定方向。
6. **真实验证全闭环**：
   - 之前写的红灯回归测试转绿，相关测试与类型/lint 全绿。
   - 按用户指定的设备与运行方式（如热更新、真机、桌面实测）跑真实用户路径；涉及 UI/交互时必须正反状态都测（展开+收起、浮层不遮挡按钮）。
   - 逐项核对第 2 步列出的全部入口，有项目 `verify-*` skill 时优先按它执行。
7. **按约定收口**：如果用户要求提交、推送、PR 或合并，继续执行 [`ship.md`](ship.md)；否则汇报完清晰停在当前验收点。

**回复必含**：根因（附文件/行号与现场证据）、改了什么、逐个入口的真实运行验证结果（明确标 `实测 / 未验证`）。
