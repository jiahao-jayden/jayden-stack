# Shipping（独立验证并合并）

**你对最终落进主干的代码负全责。每个 PR 必须独立验证通过，从最底层连续合入已验证区间，合完立即读回确认。**

1. **先确定托管平台，再为每个 PR 做独立验证**：
   - 默认用 `gh`；若 `origin` CLI 解析该仓库则用 `origin pr`。绝不依赖 `gt`。
   - **独立验证原则**：由**没写这段代码**的验证代理，在真实运行面上按用户路径（优先项目 `verify-*` skill）对比父分支与当前 head，给出 `PASS`、`PASS+NOTES` 或 `FAIL` 结论。写代码的作者容易只测自己以为做对了的东西；绿 CI 和机器人审批也不能替代真实用户路径验证。
2. **只合入从栈底向上连续通过验证的区间**：
   - 从最底层的未合并 PR 往上扫，遇到第一个没有 `PASS` 或 `PASS+NOTES` 的 PR 就停——它下面的连续段是本次可合区间，它的上一个就是上限（ceiling）。
   - 位于未验证 PR 之上的已验证 PR 必须等待，除非它完全不依赖下层代码且重新变基到主干后拿到针对主干的新验证结论。
3. **复核验证结论是否仍然覆盖当前代码（`git patch-id` 校验）**：
   - 结论覆盖的是“补丁内容”，链式 rebase 会改变 SHA。用 `git patch-id` 对比验证时 SHA 与当前 head：
     - patch-id 一致 → 原验证结论继续有效；
     - 差异仅在测试、文档或 lint 配置且目标构建产物除可解释噪声（如内嵌 commit SHA）外完全一致 → 写清噪声文件后可延续该验证通道，但新改动本身仍需新鲜检查；
     - 逻辑代码已变或涉及 dev server 等无法比对构建产物的运行面 → 必须重跑验证。
4. **自底向上，一次合入一个 PR，并强制读回核验**：
   - 总是合入可合区间里最底层的未合并 PR：`gh pr merge <pr> --squash` 或 `origin pr merge <pr>`（注意 GitHub 上若 base 仍是父分支而不是主干，会合进父分支而非主干）。
   - **必须读回 PR 状态确认真实合入**：`gh pr view <pr> --json state,mergedAt,baseRefName` 或 `origin pr view <pr>`。因为合并命令返回成功可能只是进了 merge queue 或开了 auto-merge，**只有读回 `MERGED` 且 `baseRefName` 为主干才算真正落地**。
   - 仅当当前 head 已被验证覆盖时才允许开 `--auto`。
   - 底层 PR 落地后，立即把紧邻的上层 PR base 切回主干（`gh pr edit <pr> --base <trunk>`），将补丁移到最新主干并用 `--force-with-lease` 推送，用第 3 步的 `patch-id` 规则复核验证有效性，等 CI 全绿后合入下一个。
5. **合入过程中不乱动栈**：除第 4 步顺次把下一个 PR 迁到主干外，不顺手修改正在等待合入的分支或 base；如果合并卡住，先查清卡点再动。
6. **在上限处停下**：想继续合入上限之上的 PR，必须重新从第 1 步拿到新验证结论。

**回复要求**：本次可合区间与上限、每个 PR 的验证结论与验证者、实际合入清单及读回确认结果（SHA / 状态）、下一个未合 PR 缺什么条件。
