# Perf issue（修复一次性能问题）

**你对测量叙事负全责。先量、再规划、再验证数字；绝不靠读源码脑补性能瓶颈。**

每次改动都必须绑定前后实测数据。如果是围绕同一个指标做多轮持续实验打磨，改走 [`hillclimb.md`](hillclimb.md)。

1. **先抓基准数据并用 `benchmark-checklist` 校验**：
   - 在真实运行面与目标设备上采集优化前基准 trace/耗时/内存（严守用户指定的设备与运行方式）。
   - 用 **benchmark-checklist** skill 的七问核对基准以及后续每一个数字，确认瓶颈限制器（limiter）且排除“没真正执行工作”的假数字。
2. **对照数据追踪源码，按「七条性能口诀」从省到贵思考**：
   先跑再下结论，绝不凭空宣称“已经到性能上限”。按以下顺序寻找突破口，前一条达标就停手：
   1. **干脆不做**：停掉没人消费结果的计算，比把算它变快强十倍。
   2. **做一次就别重复做**：缓存、记忆化、合并重复查询/渲染。
   3. **少做一点**：降频、裁剪规模、只算可见区域。
   4. **晚点再做**：懒加载、延后到真正用到时。
   5. **趁用户不注意时做**：空闲预处理、预取。
   6. **并发着做**：拆掉不必要的串行等待。
   7. **用更便宜的办法做**：换数据结构、算法或底层实现。
3. **基于 trace 规划修复并逐片验证**：
   - 跨模块边界先跑 **architect**。
   - 按「拆成可验证切片」每次只验证一个改动，委派给边界清晰的 `worker`，审查 diff 后再抓修复后的 trace；不要把三个未单独验证的优化混在一起导致无法归因。
   - 连续 3 轮无实质收益或引入正确性回退时立刻停下复盘。
4. **对比原始产物**：
   - 用脚本解析并对比前后产物（如 JSON 导入 SQLite 聚合 diff），不要靠肉眼扫大日志。“结果不明确（Inconclusive）”或在错的运行面上测的都不算通过，直接标红。
   - 同时确认未破坏任何行为契约与 UI 观感。
5. **把测量口径与前后数字写入 PR 并收口**：执行 [`opening-a-pr.md`](opening-a-pr.md)。

**回复要求**：测试口径、优化前基准、优化后结果、变化幅度（含样本数与波动区间）、限制器说明、以及原始测量产物路径。
