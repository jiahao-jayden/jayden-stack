# Playbook：新功能开发（Feature）

**先想清形状再写代码，按最小可验证切片推进，每一个用户入口都要真实跑顺。**

1. **澄清意图与多入口清单**：先用两三句话确认目标、明确的非目标、约定的最终交付态（本地改完 / 提交 / PR / 合入 `main` / 发版），以及本次覆盖的全部端与入口（如桌面端、移动端、侧栏、弹层、设置页），全部写入 todo。若有必须由用户拍板的产品分叉，先问清并给推荐选项。
2. **先读现有结构再设计**：派 `scout` 摸清相关模块的现有约定、可复用组件与依赖（优先用已有库与成熟模式，不重造轮子）。
3. **跨模块先画骨架（Architect）**：只要改动跨越文件或模块边界，先对比至少两种接口/状态归属方案，选出满足以下条件的那一种再写实现：
   - 每份状态只有一个明确所有者；
   - 同类事情只有一种做法（过时接口同步迁完并删掉，不留兼容层）；
   - 调用方需要知道的细节最少。
4. **按可验证切片分步实现**：把大改动拆成小步、每步可独立跑绿的切片。边界清晰的子任务可派 `worker` 并行执行（文件范围不重叠）。保持最小改动，不顺手重做无关代码。
5. **补强自动化验证**：
   - 写面向行为的测试（不绑死内部私有实现）。
   - 若涉及状态机、协议编解码、解析器、同步/并发合并或复杂数据变换，优先补属性测试（Property Test，如 `fast-check` / `proptest`）或等价性对比测试。
6. **真实环境端到端实测**：
   - 严格遵守用户指定的设备与运行方式（热更新、真机、禁模拟器等），有项目 `verify-*` skill 优先使用。
   - **UI/交互改动必做正反检验**：展开与收起动画、打开与关闭、浮层/菜单是否遮挡按钮、空态/加载态/报错态。
   - 对照第 1 步的多入口清单逐项跑通并留证据；遇到连续三轮修不过立刻熔断找人。
7. **中高风险改动过一遍跨厂商评审**：涉及多模块、状态同步、安全/权限或重要核心路径时，在收口前按 `references/host-dispatch.md` 跑一次跨厂商只读 `reviewer`（优先从 base 分支读 `REVIEW.md`），亲自复核每条问题后再修。
8. **按约定终态收口**：继续执行 [`ship.md`](ship.md) 直到达到第 1 步约定的终态。

**回复必含**：核心设计取舍、改动摘要、多入口逐项实测证据（含未验证项说明）、是否已达到约定终态。
