# Playbook：探索与验证（Explore）

**核心边界：不动正式业务代码。你的交付物是“带实证的真相、决策或评审结论”，不是补丁。**

本剧本覆盖四类只读/非正式任务——先判断属于哪一种，再走对应步骤：

## A. 查根因 / 排查问题（Investigation）

1. **先抓现场，再看源码**：优先查真实日志、报错堆栈、网络请求/响应、数据库记录或进程状态；不要只盯着静态代码猜发生了什么。
2. **用自己的话定界**：用一两句话写清“预期是什么、实际发生了什么、影响范围在哪”；若问题有歧义，说明你的理解并开始查，用户可随时纠偏。
3. **并发侦察多条假设**：把独立假设派给只读 `scout` 子代理并发核查，每条假设必须用代码路径、日志或只读复现命令验证或排除。
4. **追到根因才停**：问清为什么会发生，而不只是报错出现在哪一行。如果过程中顺手发现了修复方案，记下来但**不要直接改业务代码**——等用户决定转入 `/build`。

**回复结构**：现象与范围、已确认根因（附文件/行号/日志片段）、已排除的假设、每条结论标注 `实测 / 推断 / 未验证`、下一步修复建议。

## B. 读懂架构 / 追溯历史（How / Why）

- **问“怎么工作的 / 放哪一层合理”（How）**：派只读 `scout` 按调用链和状态归属梳理想法，给出一份读完就能上手改代码的架构心智模型，附关键文件与符号位置。
- **问“为什么当年这样写”（Why）**：查 `git log`、commit message、PR/Issue 讨论和决策文档；直接引用原始记录，自己补全的推理显式标为 `推断`，记录没写明的地方如实说“记录无记载”。

## C. 一次性原型与方案对比（Prototype）

**目标是用最低成本拍板设计或技术分叉，代码质量不重要，原型用完即扔。**

1. **先明确要拍板的问题**：要决定什么布局、交互、动效、信息密度，或是哪条技术路线/时序表现更好？没有明确待决策点就不做原型，直接转 `/build`。
2. **在隔离临时目录搭建**：放在独立临时目录（绝不污染正式源码树）。视觉/交互决策用最轻的 HTML/CSS/JS 或最小预览页；行为/时序决策用最小独立脚本。不引入正式工程抽象、不写单元测试。
3. **同屏放多方案切换**：当方案有多种选择时，在一个切换器（按钮或快捷键）里把多个备选方案做出来并标清名称，方便直观横评。
4. **真实观察**：视觉原型截图并实际操作正反交互（展开/收起、遮挡）；行为原型打印真实耗时与输出。
5. **明确交代原型是抛弃式的**：给出各方案权衡、证据与你的推荐，用户选定后再转入 `/build` 做正式实现。

## D. 跨厂商对抗式评审（Interrogate）

**目标是用“挑刺视角”提前打爆隐患，只保留拿得出来证据的发现，不改代码。**

1. **锁定评审范围与意图**：默认评审当前分支相对 base 分支的 diff（含工作区未提交改动），先复述本次改动的目标意图。
2. **从 base 分支读 `REVIEW.md`**：如果仓库存在 `REVIEW.md`，用 `git show <base>:REVIEW.md` 读取，作为评审准则。
3. **派跨厂商只读 `reviewer`**（见 `references/host-dispatch.md`）：要求它专门找正确性漏洞、漏掉的端/入口、状态竞态、安全或数据风险，且每条发现必须给代码证据或复现命令。风格和命名偏好不要凑数。
4. **主会话亲自复核**：对 `reviewer` 报出的每条发现，主会话对照源码或重跑复现命令核实，过滤误报。
5. **按四类输出**：`必须修` / `可考虑` / `原有缺陷` / `已驳回`（没问题就直接写“未发现阻塞项”）。
