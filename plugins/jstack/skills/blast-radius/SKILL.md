# Blast radius（爆炸半径与 5 级确定性证明）

与 `how`（它怎么工作）和 `why`（为什么这么写）配套：`blast-radius` 专门回答**“这个改动会在 diff 之外把哪里炸掉？”**

**列调用方不是你的工作**——grep 一秒钟就能列完。你的真正任务是找出 **grep 根本搜不出来的隐蔽破坏**。

## 绝不轻信自己写出的漂亮分析

一份看起来头头是道的爆炸半径文字分析毫无价值——不管真假它读起来都很像真的。所以绝不要只交一篇“我认为安全”的小作文：**找出整个改动之所以安全的 1–2 个核心前提事实，然后跑真实代码去证明它。**

### 确定性 5 级阶梯（How sure are you）

对改动安全性依赖的每一条核心事实，尽可能往低成本能达到的最深层级推，并**如实写明停在了第几级**：

1. **嘴上说安全**：毫无价值。
2. **指到真实代码行**：给出真实的 `file:line` 或第三方库自身源码位置。
3. **推演坏路径不可达**：一步步走通失败路径，证明它无法触发。
4. **跑真实代码验证**：写一个小脚本或测试，直接 import 应用实际打包的同一份库、调用你担心的精确函数，一旦假设为假就大声失败。
5. **在运行中的真实应用里复现/验证**。

第 4 级通常只需要十几行脚本，性价比极高。

## 执行步骤

1. **通读完整改动**：diff 增删改了哪些符号、改变了哪些外部行为——尤其留意 diff 表面没写出来但隐含改变的契约（拉取完整 PR 与所有 commit）。
2. **找出“它之所以安全的唯一核心事实”**：绝大多数看似高危的改动，背后其实依赖某一条关键事实（比如“这个调用只清理已经失效的缓存项，不触碰活跃连接”）。把精力集中在这条核心事实上——只要它成立，一大片担忧瞬间清零；只要它不成立，立刻抓到大 Bug。不要罗列几十条“也许会”。
3. **往 grep 停下的地方继续挖**：
   - 去读你调用的第三方库源码、锁定的真实版本与本地 patch；
   - 算清楚执行时序：微任务、卸载与 teardown、框架渲染周期差异；
   - 追踪符号搜索扫不到的隐式契约：HTTP/IPC 返回的 JSON 结构、数据库列、二进制线协议（wire format）、跨语言（TS ↔ Rust ↔ Swift）共享的同一批字节、Feature Flag、以及下游三跳之外的消费方。
4. **诚实评估每条风险**：给出真实的触发概率和破坏代价。把“已确认风险”与“查过且排除的风险”分开列；每条必须带真实 `file:line`（搜不到调用方本身也是有效结果），绝不捏造调用方或 API。
5. **跑代码证明核心安全事实**：写出最小脚本或测试跑真实代码，直接把实际运行输出贴出来。
6. **高危大改动走跨厂商多视角**：规模大或影响面广的改动，按 **arena** / **interrogate** 派多厂商模型并发排查同一问题再合并结果，不同模型会挖出不同的隐蔽雷。

## 输出格式

- **改动实际做了什么**：含 diff 表面看不出来的隐含行为变化。
- **它之所以安全的唯一核心事实**：明确陈述、标明推进到了确定性第几级（1–5），并贴出真实运行证明；若没能证明，直白写 `未证明`。
- **已确认风险**：逐条写明怎么坏、精确 `file:line`、触发概率与后果、验证方式及实测输出。
- **已核查并排除项**：查了什么、为什么安全。
- **合并前建议补的最小防线**：抓这个真 Bug 成本最低的测试或复现脚本（附你刚写好的脚本）。
