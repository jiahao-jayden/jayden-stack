# Correct（把反复踩过的坑固化进结构）

当操作者在同一个仓库里不得不反复提醒同一类错误时，不要再多写两行“请务必注意”——**改造仓库结构，让下一个 Agent 根本犯不了这个错。**

按这个真实前提来设计仓库：每个新来的 Agent 只看到了它打开的那几个文件，会照抄手边最近的例子，并走能让代码编过的最短路径。好的仓库能让“只看一个文件写出来像对的代码”在全仓层面也真的对。

## 1. 先从历史记录归纳错误类别

读最近的 commit、revert 记录、PR 评审评论、Agent 规则文件以及解释 workaround 的注释，把反复踩的坑归类。**同一类错只要出现过 2 次就算一个有效类别。**

## 2. 按能奏效的最高层级逐类根治

严格按以下优先级，能用高层绝不用低层：

1. **用架构彻底消灭它**：每份状态只留唯一所有者，同类任务只留唯一受支持的做法；隐藏内部实现让错误导入直接报错；用单一真相源替代手工同步列表；删除会被 Agent 照抄的旧路径和死代码。
2. **用类型系统让坏代码编不过**：如果坏写法依然能通过编译，就加一条 Lint 或 CI 检查，**报错信息必须直接点名应该改用哪个文件、类型或函数**。如果旧代码里已有存量，做成增量门禁（只拦截新增违规）。
3. **用行为测试守住它**：修正或删掉那些“行为坏了却照样绿”或“只重构内部就全红”的烂测试。
4. **文档与 Agent 规则永远排最后**：只留给确实需要人工工程判断、无法机械判定的准则——因为跳过文档不会触发任何报错。

## 3. 落地并用真实历史错证明有效

立刻按类别落地最常踩的几项（每类一个干净 commit）。**每一条新加的类型/Lint/测试防线，都必须拿一次真实历史错去验一遍，确认它确实会红灯拦截**，并且本地与 CI 跑同一条命令。任何例外豁免必须写在触发行旁边，带原因、过期日期与人工批准。

## 4. 维护规则-防线对照表

如果仓库规则文件里有一条文字规定反复被违背且背后没有任何机械检查兜底，立刻升级到更高层级把它锁死；一旦某个错误在结构上已经不可能发生，果断从文字规则里删掉那条过时叮嘱。

**回复要求**：每个归纳出的错误类别、历史证据、选定的防线层级，以及为何没选更高一层级（若未选架构/类型层）。
