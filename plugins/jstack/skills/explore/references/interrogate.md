# Interrogate（对抗式只读破坏审查）

**核心规则：对手的目标是把改动或设计打爆；只有“跑得出来真实失败证据”的发现才能存活。只报告经复核的发现，绝不直接改正式代码。**

## 1. 定界与复述意图（Frame）

- **范围**：默认使用用户指定的范围；未指定时为当前分支相对 base 分支 merge-base 的完整 diff（含工作区未提交改动）。
- **复述意图**：结合用户消息、commit 历史与 PR 描述，用一两句话写清本次改动的真实目标；如果意图含糊不清，先问清用户再审查。
- **读取评审基准**：若仓库 base 分支存在 `REVIEW.md`，用 `git show <base>:REVIEW.md` 读出原文（绝不轻信本分支对评审标准的修改），一并附给对抗者。

## 2. 派出跨厂商对抗评审者（Fan out）

参考 **arena** 的隔离并发与 `../../jstack/references/host-dispatch.md` 的双宿主跨厂商规则：
- 在 Cursor 中并发派出 1–3 个跨厂商强模型只读/隔离 worktree 子代理（把工作区未提交改动同步进各隔离 worktree，绝不污染主工作区）；
- 在 Codex 中通过 `scripts/run-external.mjs` 调本机 `claude` CLI（必要时再配一个 Codex 只读 `reviewer` 交叉核验）；若外部通道 dropout 必须显式汇报。

给每个对抗者的任务书必须包含范围、复述后的意图、`REVIEW.md`（若有）以及以下硬指令：

> 试着打爆这个改动（或设计）。每一条发现都必须用**针对真实代码的运行结果**证明——比如失败的测试、最小复现脚本、或打印出错误行为的真实命令输出。针对设计或计划时，跑一个最小探针脚本或实查当前代码树。把复现脚本留在你自己的隔离目录里。
> 每条发现必须给出：标题、精确复现命令、它实际打印出的输出、以及意图要求它本该输出什么。
> **凡是你没有亲手跑出证据的东西全部删掉不报**——包括代码风格、命名偏好、结构洁癖，以及“万一以后有人改代码可能会出事”的假设性风险。查不出真问题时，“无经证实的发现”完全是合格结论。

## 3. 主会话亲自复核与去重（Verify）

对抗者回报后，**主会话必须亲自重跑每条发现的复现命令（或逐行对照真实代码核验）**：
- 输出确实复现失败、且该失败违背了改动意图 → 保留；
- 跑不出来、前提错误或纯属臆测 → 直接丢弃并记录丢弃原因；
- 多个对抗者发现的同一根因 → 合并为一条，并保留所有发现者的署名。

注意：与 `arena` 不同，这里**不做择优淘汰**——不同模型擅长抓不同种类的真实 Bug，凡是经验证成立的发现全部保留。

## 4. 输出格式

- **改动意图**：复述后的目标。
- **经证实的发现（按四类清晰分组：`必须修` / `可考虑` / `原有缺陷` / `已驳回`）**：每条必须附带精确复现命令、真实输出、如何违背意图，以及由哪个评审者发现。若全部被排除，直接写「未发现经证实的阻塞问题」。
- **丢弃统计**：每个评审者被过滤掉了几条及简要原因（方便评估评审信噪比）。
