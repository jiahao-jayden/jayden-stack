# verify-setup

让项目拥有可脚本化、可重复的真实端到端验证闭环（改编自 `pstack` 的 `create-verification-skill` 与 `maintain-verification-skill`）。

先检查当前仓库是否已经存在项目本地的验证 skill（如 `.cursor/skills/verify-*/` 或 `.agents/skills/verify-*/`）：
- **不存在** → 走「A. 首次生成」；
- **已存在** → 走「B. 巡检与校准」。

---

## A. 首次生成项目验证 Skill

### 1. 先采访仓库，不先打扰用户

直接从代码库、脚本和文档里摸清五件事，只问代码里完全查不到的信息：
- **用户触面（Surface）**：用户实际操作什么？桌面端、Web、移动端真机、CLI/TUI、还是 HTTP 服务？多端并存时标出主触面与其余端。
- **启动方式（Launch）**：本地开发命令、端口、环境变量、必需的前置服务或 seed 数据；明确怎样算“真正就绪可用”（不能只看进程活着）。
- **驱动工具（Drive）**：优先用仓库已有的真实驱动方式（如 `agent-desktop`、Playwright/CDP、PTY/tmux、`curl`、真机热更新等），绝不自造与真实用户无关的内部后门。
- **可观测证据（Observe）**：截图、终端日志、接口回包、数据库状态、退出码，以及证据落盘目录。
- **隔离与运行纪律（Isolate）**：能否多实例并行？有没有严格的设备/运行约束（例如：只测真机、禁止安装/启动模拟器、必须走热更新）？如果有，必须作为硬规则写进生成的 skill。

如果项目当前连启动或构建本身都是坏的，先修好或如实汇报，不要基于坏底座写一份假验证文档。

### 2. 生成 Skill 与 Feature Map

按仓库当前采用的 skill 放置位置（若同时使用 Cursor 与 Codex，优先放在共享路径或 `.cursor/skills/verify-<app>/` 并在仓库说明中标清），写入：

1. **`verify-<app>/SKILL.md`**（带完整 YAML frontmatter：`name`、`description`），必须写死真实命令与路径，不留占位符：
   - **Launch**：启动命令、就绪判据、运行纪律（如设备/热更新约束）。
   - **Doctor**：一条只读健康检查命令，回答“当前实例能不能测”（进程/端口/版本/鉴权是否正常）。
   - **Drive**：基于真实定位器（ARIA label、`data-slot`、路由路径、CLI 子命令）的操作配方，少用脆弱坐标。
   - **Evidence**：证据存放路径与验收标准——走真实用户路径、正反状态都测（展开+收起、遮挡检查）、同时验证可见界面与底层副作用。
   - **Cleanup**：只清理本次启动的实例与临时状态，绝不按进程名误杀用户自己的会话，且**清理后证据文件必须完好保留**。
2. **`verify-<app>/features/README.md` 与首批 3–5 个核心功能文件**：
   - 每个功能文件从用户视角写四个二级标题：`子功能`、`如何到达（用户视角）`、`驱动与正反检查步骤`、`常见坑与前提（Gotchas）`。
   - 若某路径因环境前提缺失无法跑通，明确标出缺失的前提，绝不降低验收标准凑通过。

### 3. 生成后必须端到端跑通一次

按照刚生成的 `SKILL.md` 自己从头跑一遍：`Launch → Doctor → 驱动至少 1 个核心 Feature → 检查证据文件存在 → Cleanup → 再次确认证据文件没被清理删掉`。
没真实跑通过的验证 skill 只是草稿，不能交付；跑挂了就修好再重跑。

---

## B. 巡检与校准已有验证 Skill（Maintain）

项目代码迭代后，Feature Map 很快会过时。本模式**只修改验证 skill 目录下的文件，绝不改产品业务代码**。

1. **检查目录索引**：核对 `features/README.md` 与实际文件一一对应，清理死链和漏项。
2. **并发读源码核对**：为每个 feature 文件派只读 `scout` 并发核查当前真实源码路径，标出文档漂移与新增但未收录的用户入口。
3. **真实跑一遍全覆盖**：按该 skill 的 `Launch → Doctor → 逐个 Feature 实测 → Cleanup` 执行，保持三条不变量：
   - 任何异常后必须先跑 `Doctor` 确认实例状态再继续；
   - 已有证据在任何清理步骤后都必须完好留存；
   - 每次失败尝试的残余进程/状态必须清理干净。
4. **分诊处理**：
   - 描述/步骤过时 → 直接修验证文档（`doc drift`）；
   - 真实功能正常但驱动脚本失效 → 修验证辅助脚本并重跑证明；
   - 真实应用功能确实坏了 → **不要改文档掩盖**，记录为产品回归报给用户。
5. **明确回报结果**：标明本次巡检结果是 `clean`（全过无漂移）、`changed`（已修正漂移并实测通过）还是 `blocked`（说明具体阻塞点）。
