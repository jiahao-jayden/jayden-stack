# Swarm（多 Worker 并发分片 / 赛跑与严苛聚合）

启动前先在 todolist 建好四个阶段：`1. Frame → 2. Fan out → 3. Aggregate → 4. Report`。

## Phase A：定界与形态（Frame）

1. **定死完成判据与最终报告形态**：写清整个蜂群必须回答什么问题或交付什么产物。
2. **选定并发形态**：
   - **分片覆盖（Partition）**：按互不重叠的文件/模块/场景切分；
   - **同题赛跑（Race）**：N 个 worker 拿完全一样的任务书赛跑；
   - **混合形态（Mixed）**。
   - 凡是涉及赛跑，**派发前先声明胜出规则**：`first pass`（首个达标即胜）、`rank all`（全部排序）或 `best-of`（挑最优）。
3. **按双宿主约定选模型**（见 `../../jstack/references/host-dispatch.md`）：常规覆盖和验证用高效主力模型；若是多模型赛跑，事先写明每条支路的模型名。
4. **严格隔离写入与强凭据约束**：
   - 凡是会写文件的 worker，各自给独立目录或 git worktree（先拆分再串行化）。
   - 凡是验证或测量 commit 的 worker，任务书里必须写死精确的 **commit SHA**；测量类任务书还必须写死**采样方法**（样本数、单样本定义、执行顺序），并要求 worker 在结果里原样回填 SHA 和方法以供核验。

## Phase B：一次性并发派出（Fan out）

在同一轮消息里把全部 N 个 worker 并发派出（`run_in_background: true`；每个任务书第一行必须要求先读 `worker.md`）。

每份任务书必须完全自包含：
- 目标、范围、精确分片或赛跑支路、验证命令、以及必须回报的格式；
- 统一状态枚举：`PASS`、`ISSUES` 或 `BLOCKED`（必须附实证）。
- 要求能证明缺陷的 worker 报 `ISSUES` 时**列出它能证明的全部问题**，不要只报第一个就停。
- 若某个 worker 中途失败掉线，用剩余 N-1 继续并如实记入 `dropout`。

## Phase C：严苛聚合与验票（Aggregate）

通读全部终态结果，严格执纪：
- **没回填任务书指定的 SHA 或测量方法的结果直接作废**，重派该 worker 一次；第二次仍漏报则直接记为 `gap`（覆盖缺口）。**`gap` 绝不算通过。**
- 分片覆盖模式下，每个必检分片都必须有有效结果；
- 赛跑模式下，严格套用 Phase A 事先声明的胜出规则；
- **绝不把 worker 的大段原始终端输出直接倾倒进汇报**。

## Phase D：输出汇总报告（Report）

向用户返回一份高度浓缩的战报：
- 分片/支路结果汇总表；
- 经证实的问题单行清单（含证据指针）；
- 任何 `gap` 或 `dropout` 列表；
- 赛跑模式下写明采用的胜出规则与胜出者。
