# Architect（先定骨架，再写代码）

写第一行业务代码之前，先追踪本次改动会触碰到的每一个子系统，**顺手扫一遍相关 `docs/adr/` 或 `docs/decisions.md`**（若存在，见 [`../../jstack/references/adr.md`](../../jstack/references/adr.md)），确认既有的不可破约束与未决方向（若新方案与旧 ADR 冲突，必须显式说明触发了哪条推翻条件，绝不悄悄绕过）。

然后**画出至少两种截然不同的设计形状**（核心类型、函数签名、状态归属、模块边界），对比后选出满足以下原则的那一种：

1. **每份状态只有一个明确所有者**（消除多源同步和隐蔽共享可变状态）；
2. **每件同类任务只有一种受支持的做法**（顺手把旧接口与兼容层划入同一波删除清单）；
3. **深模块优先，拒绝浅透传层**（窄且稳定的接口隐藏厚重实现，调用方需要知道的内部细节最少，把非法状态挡在类型系统和入口边界之外）；
4. **沿真实接缝（Seam）切分并通过删除测试**：模块边界落在可独立验证/替换的真实接缝上；凡是删掉后代码更直白的中间胶水层或单次包装，一律不建。

如果发现为了塞进新需求不得不在旧结构里反复打补丁，按「第一性原理重设计」直接提出重塑方案，而不是往上叠特判。

当设计规模很大、争议很强、或存在多种各有千秋的架构方向时，不要单打独斗手画——直接改走 [arena](arena.md) 让多模型并发赛马、跨厂商裁判打分并手工嫁接最佳方案。

**输出要求**：备选形状对比表（类型/边界/优缺点）、选定方案的精确接口草图、需要顺手清理的旧路径清单；若本次拍板踩中 [`../../jstack/references/adr.md`](../../jstack/references/adr.md) 的三条件门槛（难逆转 + 缺上下文会误改 + 真实取舍或未决方向），一并给出 10–25 行极简 ADR 草稿随本次改动落盘（不踩门槛就不写），确认无误后再进入编码实现。
