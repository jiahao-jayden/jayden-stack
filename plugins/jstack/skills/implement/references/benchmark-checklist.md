# Benchmark checklist（性能数字七问防伪核对）

凡是你要汇报一个性能数字（PR 前后对比、性能回退告警、Hillclimb 脚手架、库或配置选型对比），先用下面七问拿**真实运行证据**过一遍，不靠读代码猜。

> 如果用户只要一个随口估算的粗略量级，跑 1 次即可，但仍必须核对第 4 问和第 7 问，并明确说明“仅单次运行”。凡是涉及方案选型，绝不能用粗略单次数字拍板。

## 开跑前先做三件事

1. **先把准备说出口的结论写下来**（例如“在 6 万行数据集上导出 p50 快了 30%”）——下面七问就是用来拷打这句话的。
2. **通读测量脚本**：看清它到底计了什么时、数了什么数、忽略了什么。
3. **查机器负载**：用 `uptime` 与核数确认机器是否正被其他进程占满；停不掉背景噪声时，必须交替运行 A/B 让双方承受同等噪声并在报告里写明。

## 七问核对

1. **为什么不能再快一倍？（找限制器 Limiter）**
   在单独一轮（不计入最终跑分，因 profiler 本身会拖慢速度）里用真实剖析工具定位瓶颈：`top` / `node --cpu-prof` / `py-spy` / `perf` / I/O 等待，把热点映射回源码。**同时盯紧压测器本身**——如果发压端先打满了，你测到的其实是压测器。如果一次优化没挪动数字，先找出真正限制器再下结论。
2. **两边都在真实生产态调优了吗？（Was it tuned?）**
   两边必须都按生产方式运行：release 构建、生产参数与环境变量、批处理与事务配置、连接池、符合生产实际的冷/热缓存、一致的数据集与版本。如果一方跑在未调优默认配置（debug 构建、逐行 commit、缺索引），你比较的只是配置不是实现。选型测试中不允许“反正代码现在就这么配”来蒙混，因为用户选的是长期方案。
3. **有没有突破物理或算术上限？（Did it break limits?）**
   动笔算一笔账：吞吐字节/秒对比磁盘与网络带宽、操作数×单次成本对比 CPU 核数、声称省下的时间对比被改模块原本占比（删掉一个占总耗时 10% 的模块，整体最多快约 11%）。超过理论上限的“神速”几乎一定测错了东西（命中缓存、空操作或提前报错）。
4. **有没有隐蔽报错？（Did it error?）**
   统计失败数与非成功响应，并验证输出结果本身是正确的而不仅仅“有返回”。直接拒绝对方往往快如闪电，超时和重试则拖慢一切。脚本不统计错误数就先加上。
5. **可重复吗？（Does it reproduce?）**
   每侧至少跑 **5 轮且交替执行**（A, B, A, B...）消除预热、懒加载、缓存和系统漂移偏置。报告**中位数与波动区间**。两者的差距如果小于自身轮间抖动，结论就是“无显著差异”。
6. **在端到端里真的重要吗？（Does it matter?）**
   任何微基准旁边都要配真实数据规模与并发下的端到端用户等待路径，报出局部耗时占端到端的比例。把一个只占 1% 的函数提速十倍，用户最多快 0.9%。
7. **工作真的在计时区里发生过吗？（Did it even happen?）**
   确认请求确实打到服务端、数据确实写盘、字节确实读完、计算结果确实被消费——未被遍历的生成器、忘了 `await` 的 Promise、被 JIT 死代码消除的算式，都会吐出漂亮却全假的极速数字。

## 汇报格式

- 首句给明确裁决：`更快`、`更慢`、`无显著差异` 或 `结果不明确（inconclusive）`。
- 给出带单位的数字、样本轮次、波动区间与瓶颈限制器（如：`p50 41ms → 33ms，每侧交替 7 轮中位数，优化后区间 32–35ms，当前受限于单核 JSON 解析`）。
- 凡是声称有差异却说不清限制器、某侧未调优、或未核对第 4/7 问的，**裁决必须标为 `inconclusive`** 并写明缺口。
- PR 正文只放核心主数字，完整逐轮数据与限制器证据放附件或评论链接。
